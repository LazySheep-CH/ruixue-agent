# 检索评测方法

**没有评测集,所有优化都是"感觉变好了"。** 这份文档说明评测集怎么造、指标怎么算、
每层增益怎么量出来的。相关脚本:`scripts/build_evalset.py` · `pool_evalset.py` ·
`run_eval.py` · `tune_weight.py`。

## 指标:Recall@k 与 MRR

| 指标 | 回答什么 | 为什么需要它 |
| --- | --- | --- |
| **Recall@k** | 标准答案在前 k 个里吗 | 检索是 RAG 的**天花板**。没检索到 → 大模型手里没材料 → 重排/prompt/换模型都救不回来 |
| **MRR** | 第一个标准答案排第几(倒数) | Recall@5 里排第 1 和排第 5 得分相同,但对大模型完全不同 —— 排第 5 意味着前面 4 段无关材料在带偏它 |

Recall 看"找没找到",MRR 看"找得好不好",两个一起看才完整。实现见 `rag/metrics.py`,
标准答案是**集合**(一题可有多个正确块)。

## 评测集怎么造(无真实用户日志时)

系统未上线、没有真实 query。企业标准做法:合成 + 严格质检,上线后用真实日志逐步替换。

### 三道工序

1. **生成**(`build_evalset.py`)— 让大模型读一个块出题。题是它出的,那 (问题 → 这个块)
   就是天然的标准答案,无需人工标注。按**六类题型 × 三种角色**轮配(研发/技术服务/质检),
   保证覆盖真实用户的提问方式。按 source 分层配额(标准规范占 30%,虽然它只占语料 2%)。

2. **裁判复审** — 换一个大模型视角逐题判四关,全过才留:
   - **可答性** — 这段真能回答问题吗(否则标准答案是错的)
   - **唯一性** — 换一篇文献的类似段落也能答吗(能 → 标准答案失效)
   - **自足性** — 单独拿出来看得懂吗
   - **真实性** — 从业者真会这么问吗(挡掉"为什么公式里有笔误"这类)

   实测通过率约 30% —— 七成生成的题被毙掉。

3. **Pooling 补全标准答案**(`pool_evalset.py`)— **这一步最关键**。

### 为什么必须 Pooling

出题时只知道一个标准答案(出题的那个块)。但库里 26 万块,另一段同样能答的几乎必然存在
—— 检索器返回了它,却被判 0 分。量到的不是"检索差",是"尺子错了"。

TREC(信息检索评测标准,几十年)的解法:用**多个不同原理**的检索器各捞候选 → 合并成池
→ 裁判逐条判"能不能答" → 能答的全算标准答案。

必须用**多个原理**:只用向量捞候选,向量漏掉的(精确数字、型号)永远进不了池、永远不会被标成
标准答案,那 BM25 找到它时反而被判错。所以用向量(语义)+ 全文(词法)两路。

**效果**:补全后平均每题 2.39 个标准答案(最多 11 个),53% 的题不止一个正确答案。做一个隔离实验
(同一批题、同一个检索器,只换标签):**旧的单标签尺子把 Recall@3 低估了 28%**。

### 已知偏差(合成评测集的天花板)

- 出题时大模型看着原文,措辞偏向原文 → 分数偏高。
- Pooling 只覆盖参与的检索器能找到的东西,全新原理的检索器可能被低估(TREC 也有此局限)。
- 所以这个基线用于**对比**(A 比 B 好多少),不用于**对外报告绝对水平**。真实问题须由领域专家出。

## 当前基线(150 题)

逐层增益,每层是"开 vs 不开,只差一个参数",所以增量可信:

| 配置 | Recall@1 | Recall@3 | Recall@10 | MRR | 延迟 |
| --- | --- | --- | --- | --- | --- |
| 纯向量 | 0.587 | 0.753 | 0.853 | 0.687 | ~190ms |
| + 混合 BM25 | 0.647 | 0.827 | 0.900 | 0.744 | ~420ms |
| + 重排 | **0.807** | **0.927** | **0.953** | **0.866** | ~1500ms |

- 混合改善**召回**(能不能找到),重排改善**精排**(排得对不对)。痛点 R@1 是排序问题,所以重排增益最大(+16)。
- 分组诊断(见 `run_eval.py --ab`):"数值查询"类天花板最低 → 精确匹配是弱项;"条件推荐"类找得到但排不上去 → 重排的用武之地。一个总分说明不了该修哪儿,分组才行。

## 超参怎么选(不是手调挑最高)

`tune_weight.py` 做三件事,这是企业标准:

1. **交叉验证** — 在一部分题上调、另一部分上验证,防止过拟合(在调参的数据上报成绩)。
2. **细扫看形状** — 分清"平台"(稳健)还是"尖峰"(脆弱)。
3. **自助置信区间** — 重抽 1000 次看差异分布,分清真提升还是噪声。

结论:融合权重 0.2~0.7 是平台(选哪个没统计区别),但"混合优于纯向量"显著(置信区间不含 0)。
**"我调到了 X,效果最好"是外行;"我证明了改动显著有效,而具体值在稳健区间内"是内行。**

## 复现

```bash
uv run python scripts/build_evalset.py --n 150     # 造题(生成+复审)
uv run python scripts/pool_evalset.py              # 补全标准答案(pooling)
uv run python scripts/run_eval.py --ab             # 纯向量 vs 混合
uv run python scripts/tune_weight.py               # 交叉验证 + 置信区间
```
