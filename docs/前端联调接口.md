# 前端联调接口

前端统一请求同源 `/api`，开发环境由 Next.js rewrite 转发到 FastAPI；业务代码不应写死后端域名。

## 认证

| 方法 | 路径 | 请求/响应 |
| --- | --- | --- |
| `POST` | `/api/auth/register` | 请求 `{ "username": string, "password": string }`；返回 token 信息 |
| `POST` | `/api/auth/login` | 请求同上；返回 `{ access_token, token_type, username, expires_in_days }` |
| `GET` | `/api/auth/me` | 校验登录态；需 `Authorization: Bearer <token>` |

除注册、登录和健康检查外，下面的接口都携带 Bearer Token。前端收到 `401/403` 才清除登录态；网络故障或 `5xx` 不会误登出用户。

## 流式任务主链路

`POST /api/chat/stream`

请求：

```json
{
  "thread_id": "前端生成的会话 ID，最长 64 字符",
  "message": "用户问题，最长 2000 字符"
}
```

响应类型为 `text/event-stream`。每个 SSE 帧的 `data:` 是以下 JSON 之一：

```ts
type StreamEvent =
  | { type: "run"; run_id: string }
  | { type: "thinking"; text: string }
  | { type: "tool_start"; name: string }
  | { type: "tool_end"; name: string }
  | { type: "answer"; text: string }
  | { type: "error"; text: string }
  | { type: "done" };
```

约定：

- 第一帧为 `run`，前端立即持久化 `run_id`。
- `thinking` 和 `answer` 都是增量文本，需要按到达顺序拼接。
- `error` 后向用户展示原因和“重新运行”；`done` 结束生成态。
- 用户点击“停止接收”只中断浏览器连接，后端任务仍会完成并落库。

## 断线恢复

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/chat/runs/{run_id}` | 查询运行状态与最终结果 |
| `GET` | `/api/chat/runs/{run_id}/stream` | 从头补发该运行已有事件，并继续等待后续事件 |

状态查询响应：

```json
{
  "run_id": "uuid",
  "status": "running | succeeded | failed",
  "question": "原问题",
  "answer": "最终答案或 null",
  "error": "失败原因或 null"
}
```

页面刷新时，前端先查询状态：仍在运行就订阅恢复流，已经结束就直接回填答案或错误。

## 运维探针

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/health` | 存活检查；工作台每 30 秒刷新在线状态 |
| `GET` | `/api/health/ready` | 就绪检查；供部署和运维判断数据库等依赖是否可用 |

## 前端对应实现

- HTTP/SSE 解析：`frontend/src/core/api.ts`
- 线程、消息、运行恢复：`frontend/src/core/store.ts`
- 事件类型：`frontend/src/core/types.ts`
- 页面联调入口：`frontend/src/app/page.tsx`
