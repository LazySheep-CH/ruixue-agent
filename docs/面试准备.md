# 面试准备:把这个项目讲透

这份文档的组织方式不是"代码怎么写的",而是**"面试官会怎么问"**。

真实面试的形状是:**项目是主线,八股是被主线拉出去的支线,答完还要能接回来。**

```
你 → 讲项目某个点
他 → 拐进八股(为什么用 B+树 / Redis 持久化 / 线程池参数)
你 → 答完八股
他 → 拐回项目("那你那条查询走索引吗?EXPLAIN 看过没?")   ← 分水岭
```

**中间那段谁都会背,最后那段没做过的人编不出来。** 所以每条追问链的重点都在最后一击。

## 零、开场:项目介绍的三个版本

### 30 秒版(自我介绍时用)

> 我做了一个地膜领域的智能体系统。用户用自然语言问"新疆尉犁种棉花该用什么配方的降解膜",
> 系统会自己去查当地土壤和气候、调三个机器学习模型预测性能、检索文献标准,给出带出处的建议。
> 技术上是 LangChain create_agent 的 ReAct 循环 + 七层中间件 + 混合检索 RAG,
> 有 33 题的 agent 级评测集和完整的部署编排。

### 2 分钟版(面试官说"详细说说"时用)

按**三层**讲,每层给一个数字:

1. **知识层(RAG)**:1578 篇文献标准 → 262,782 个检索块。混合检索(向量 + BM25 + RRF 融合 + 交叉编码器重排),
   Recall@1 从纯向量的 0.587 提到 0.807。
2. **能力层(工具 + 预测模型)**:9 个叶子工具 + 2 位专家子 agent。三个性能预测模型
   (降解率 R²=0.950 XGBoost、水蒸气透过率 0.877、拉伸强度 0.852,都是 5 折交叉验证)。
3. **工程层(Harness)**:七层中间件、异步运行、三道流量闸门、优雅停机、
   33 题评测集(32/33,噪声地板 0%)、318 个测试、一条命令部署。

### 5 分钟版

## 一、一个请求的六站旅程(架构主干)

```
浏览器 / curl
   │
   ▼
① nginx(80,唯一入口)           TLS 终结 · 同源合并 · SSE 直通
   │  /api/* → 撕掉前缀转后端;其余 → 前端
   ▼
② 三道闸门                        鉴权(你是谁)→ 限流(频率)→ 配额(总量)
   ▼
③ 容量闸门 + 创建 Run             全局并发上限;拿 run_id;转后台跑
   ▼
④ 中间件链(七层洋葱)            注入防护 → 技能 → 刹车 → 压缩 → 重试 → 计时 → 兜底
   ▼
⑤ ReAct 循环                      想 → 挑工具 → 调 → 看结果 → 再想
   ▼
⑥ 工具层                          RAG · 土壤 · 气候 · 预测 · 用量 · 派专家
```

**每一站都能被单独追问,下面逐条给追问链。**

## 二、追问链(核心部分)

### 链 1:nginx —— 为什么单实例还要反向代理

**项目点**:app 和 web 都不映射宿主机端口(`expose` 而非 `ports`),nginx 是唯一入口。

**会被拉出的八股**:正向/反向代理区别、负载均衡算法、CORS 同源策略、TLS 握手。

**怎么答**:
- 我们**不是**为了负载均衡(只有一个实例)。三个真实理由:
  ① **TLS 终结** —— 证书只装一处、只续一处期,后端永远说明文 HTTP;
  ② **同源合并** —— 前端和 `/api` 都走 80,浏览器看来同源,CORS 问题直接消失;
  ③ **收窄攻击面** —— app 只在 docker 内网可见。
- ⚠ 分清层次:**nginx 保护的是 app 层;数据库靠的是端口只绑 `127.0.0.1`**,两码事。

**最后一击(SSE 三件套)**:
> "nginx 默认会把上游响应攒够一块再转发,对普通 JSON 是优化,对 SSE 是灾难 ——
> 用户盯着转圈几十秒然后答案唰一下全出来,流式白做了。所以 `/api/` 那段配了
> `proxy_buffering off` + 后端响应头 `X-Accel-Buffering: no` + `read_timeout 600s`。
> **而且我一开始把 X-Accel-Buffering 写成了 nginx 的 proxy_set_header —— 那是贴在
> 寄给后端的请求上,方向反了,纯摆设**,是给人讲解时被问'双保险是什么意思'才发现的。"

**另一个最后一击(upstream 解析)**:
> "nginx 默认在**启动时**把上游域名解析成 IP 并一直用它,容器一重建 IP 就变、502 且不自愈。
> 所以我们写的是 `set $backend "app:8000"` + `resolver 127.0.0.11 valid=10s`,改成按 TTL 重新解析。
> 代价是失去到上游的 keepalive,这个量级下不值一提。"

### 链 2:限流 + 配额 —— 为什么要两道

**项目点**:限流 20 次/分钟,配额 200 次/天,计数都在 Redis。

**会被拉出的八股**:限流算法(固定窗口/滑动窗口/令牌桶/漏桶)、Redis 持久化(RDB vs AOF)、
Redis 原子性、分布式锁。

**怎么答**:
> **限流护的是系统,配额护的是钱包。**
> 只有限流:他每分钟规矩打 20 次,一天 28800 次,系统不崩但账单崩了。
> 只有配额:他一秒内把 200 次全打出去,总量没超但瞬时并发把服务压垮。
> 一个管**速率**,一个管**总量**。

**最后一击(为什么必须在 Redis)**:
> "我们跑 2 个 worker 进程。计数如果存进程内存,两个 worker 各算各的,**限额直接 ×2**,
> worker 越多漏得越多。所以必须放共享存储。
> 配额用 `INCR` 而不是'读出来+1再写回去' —— 后者两个 worker 同时读到 99 都写 100,会丢计数。
> key 用 `前缀:日期:用户` 分桶,**新的一天天然从 0 开始,不需要定时任务清零**。"

**最后一击(降级策略)**:
> "Redis 挂了我们选 **fail-open**(放行)。因为这道门守的是钱,损失有限可恢复;
> 为防这个而让整个服务瘫痪,代价远大于风险。
> **但如果是鉴权依赖 Redis,必须反过来 fail-closed** —— 守数据的门坏了就该关门,
> 不能'门锁坏了把门大开'。"

### 链 3:异步 Run —— 这个项目最值钱的设计

**项目点**:agent 不绑 HTTP 请求,跑在后台线程池;Run 状态在 PG,事件流在 Redis。

**会被拉出的八股**:线程 vs 进程、线程池参数、GIL、消息队列、幂等、SSE vs WebSocket。

**怎么答(先讲问题)**:
> "agent 回答一个问题要 30 秒到几分钟。这期间用户会刷新页面、切微信、锁屏、进隧道。
> 如果 agent 跟着 HTTP 请求跑,连接一断生成器被取消,agent 半路死掉 ——
> **钱花了、答案没了、用户还得重问**。"

**解法**:
```
POST /chat/stream
  ├─ ① PG 建 Run 记录 → 拿 run_id(取件码)
  ├─ ② agent 丢进后台线程池(不绑请求)
  └─ ③ 返回 SSE,第一条就下发 run_id
       后台每产出一段写 Redis Stream,SSE 从 Redis 读了推给客户端

断线 → 只断了 SSE,后台照跑完落库
回来 → GET /chat/runs/{run_id} 拿结果,或 /stream 从头补发
```

**三个角色的边界(必背)**:
| | 职责 | 丢了会怎样 |
|---|---|---|
| PostgreSQL | Run 的权威状态和最终答案 | 不能丢 |
| Redis Stream | 过程事件(TTL 1 小时) | 只影响"回放过程",不影响最终答案 |
| 后台线程池 | 真正在跑的 agent | 进程死则全没 → 靠 reap_stale 兜底 |

**最后一击(为什么事件流不能放内存)**:
> "多 worker 下,用户刷新后的请求**可能落到另一个 worker**。事件存在产生它的那个进程内存里,
> 另一个进程读不到,重连就失败。"

**最后一击(孤儿清理)**:
> "进程被强杀时,后台线程没了但库里还写着 running,用户会等一个永远不来的答案。
> 两条兜底:**正常停机**主动把在途的落库为 failed;**异常重启**靠启动时的 `reap_stale()`
> 把超过 15 分钟还 running 的标记失败。后者只在进程启动跑一次就够 ——
> 因为线程活在内存里,**服务重启过就意味着库里所有 running 都是孤儿**。"

**如果被问"为什么不用消息队列"**:
> "现在是进程内有界线程池,单机几十人、一次 30 秒,够用且零额外运维。
> **知道下一步是消息队列,触发条件是两个**:要独立扩容 worker,或任务长到重启丢了很心疼。
> 换过去的收益是崩溃隔离 + 任务可持久重放,代价是多一个 broker 要运维、跨进程排查变难。"

### 链 4:中间件链 —— Harness 的核心

**项目点**:七层中间件,列表越靠前包在越外面(洋葱结构,不是流水线)。

```
PromptInjectionGuard ┐ 最外
  SkillInjection     │
    ModelCallLimit   │
      Summarization  │
        ModelRetry   │
          Timing     │
            ToolError│
              ★ 真正调模型/工具   ← 最内
```

**会被拉出的八股**:装饰器/AOP、责任链模式、洋葱模型(Koa/Express 中间件)。

**为什么这么排(每条都有理由)**:
- **注入防护最外**:① 安全检查要在花钱之前;② **后面所有组件都得在它保护之下** ——
  摘要压缩会把用户原文喂给另一个模型,防护在它后面的话,摘要模型先被攻击了。
- **死循环刹车在压缩之前**:已经到上限就该立刻停,不能先花钱做摘要、再发现该停了。
- **工具错误兜底最内**:第一时间接住异常。在外层的话异常会先穿过重试层,
  可能对"参数写错"这种异常傻乎乎重试三次。
- **计时包在错误处理外面**(最精妙的一处):这样**失败的调用也能记下耗时**。
  反过来的话异常会冲过计时层,那行记录根本不执行 —— 而"工具卡了 30 秒才失败"
  和"瞬间失败"是完全不同的两种病,恰恰是排障最需要的数字。

**对应面经题「Model + Harness 才等于生产级 Agent」**:
> "光有模型 = 一个会聊天的 API。Harness 补的是五件事:安全(注入防护)、
> 上下文(摘要压缩)、成本(轮次上限)、稳定(重试 + 工具兜底)、可观测(计时 + trace)。
> **证据**:我们评测跑 99 次真实对话,发现 RAG 内部那次 LLM 调用不在重试中间件之下,
> 一次网络抖动整个知识库工具就挂 —— 99 次里踩中 6 次。
> 原则不是'加重试',而是**每个模型调用点恰好有一层重试**。"

### 链 5:多 Agent —— 子 agent 就是一个工具

**项目点**:`delegate_to_expert` 工具 + 2 位专家(文献检索、配方优化)。

**会被拉出的八股**:多 Agent 协作模式(Supervisor / Hierarchical / Swarm)、防递归、上下文隔离。

**怎么答**:
> "我们用的是 **subagent-as-tool**(≈ Supervisor 模式):主 agent 是项目经理,
> 专家是一个工具。`deepagents` 官方包的 `SubAgentMiddleware` 是**同一个模式** ——
> 它的文档第一句就是 'providing subagents via a `task` tool'。"

**四个设计点**:
- **防递归**:专家的工具集**不含** delegate,想再派活也派不了 —— 结构上杜绝,不靠提示词约束。
- **上下文隔离**:专家**不传 checkpointer**,每次调用无状态、无残留;专家看不到主对话历史。
- **最小权限**:每位专家只拿该拿的工具。
- **成本**:专家用便宜模型(flash)。

**最后一击(并行)**:
> "两位专家并行跑是**框架白送的** —— LangGraph 的 ToolNode 本来就并行执行同一轮的多个工具调用。
> 我实测过:一轮 3 个各 1 秒的工具,总耗时 1.03 秒。
> **但要知道代价**:两个子 agent 并行 = 两条 LLM 循环同时跑,并发 API 调用翻倍 ——
> 这正是容量闸门必须存在的理由。"

**为什么只有 2 位专家**:
> "子 agent 只在三种情况下赚钱:内部要转很多圈、需要更窄权限、能用更便宜模型。
> 反例是'用量计算专家' —— 那个工具一次调用就出结果,套一层子 agent 反而多付一整条 LLM 循环。
> **而且每加一位专家,主 agent 派错的概率就上升**,评测里 tool_route 8/8 有一部分是'选项少'换来的。"

### 链 6:RAG —— 幻觉的三层原因

**项目点**:1578 篇 → 262,782 块;向量 + BM25 + RRF + 重排;R@1 0.807。

**会被拉出的八股**:向量检索原理、BM25、RRF、重排、chunk 策略、幻觉治理。

**对应面经题「RAG 幻觉三层原因分别怎么治」** —— 这题我们答得最满:

| 层 | 病因 | 我们的治法 | 数据 |
|---|---|---|---|
| 没召回到 | 检索召回率不够 | 混合检索(向量补语义、BM25 补精确词)+ RRF 融合 | R@1 0.587 → 0.647 |
| 召回错了 | 排序不准 | 交叉编码器重排 | 0.647 → **0.807** |
| 模型乱答 | 没约束 | grounding:只依据资料、数字与原文一致、**每条结论标出处** | — |

**最后一击(Small-to-Big)**:
> "检索用**子块**(短、语义聚焦、命中准),送给模型的是它的**父块**(长、上下文完整)。
> 这解决了'切太碎则语义断裂、切太大则检索不准'的矛盾。"

**最后一击(时效性,这个最出彩)**:
> "评测里发现一个危险行为:问'现在 PBAT 多少钱',agent 从知识库翻出 2023 年文档里的价格
> **当成现价答了** —— 用户会拿这个数去采购。
> 我先在系统提示里写'不要把历史价当现价',**跑评测测出来完全没用**(未超噪声地板),
> 成本反而 +14%。所以改成**结构性修法**:让检索出处带上文献年份和标题。
> 模型看到的不再是一段无时间的事实,而是'《XX报告》(2023 年)'。
> 改完那道题从 0/3 变 3/3。**能用结构解决的,不要留给模型自觉。**"

### 链 7:评测 —— 凭什么说新版本更好

**项目点**:33 题冻结评测集,7 个类别,当前 32/33,噪声地板 0%。

**会被拉出的八股**:评测指标、LLM-as-a-Judge、A/B 测试、显著性检验。

**这是最能拉开差距的一条,因为大多数人答不上"怎么证明变好了"。**

**主指标为什么坚持客观可判定**:
> "不用 LLM-as-a-Judge 打主分 —— 同一版本跑两次裁判给分能差好几个点,
> 那'新版本 +2%'到底是真提升还是噪声?**没法回答的指标等于没有指标。**
> 所以主指标全是规则可判的:工具集合匹配(按集合不按顺序)、关键点正则/数值容差、
> 系统提示逐字泄露检测、成本三件套。"

**七个类别用七把尺子**:
> "用一把尺子量所有题会得到一个没有含义的平均分。注入题只有'挡住/没挡住',
> 不存在'答得好不好';refuse 题答得越详细反而越糟(在编)。
> 其中两类最常被忽略:**no_tool**(agent 的典型退化不是不会用工具,而是什么都用一遍,又慢又贵)、
> **clarify**(信息不足却直接给数,用户看不出它是猜的)。"

**噪声地板(杀手锏)**:
> "先量仪器精度,再拿它量东西。同版本跑三轮:
> 默认温度下 84.8% / 93.9% / 97.0%,**极差 12.1% ≈ 4 道题** ——
> 这把尺子测不出任何小于 4 道题的改进,拿它做 A/B 等于掷骰子。
> 根因是评测在用一个**没设 temperature** 的模型(服务端默认 1.0)。
> 压到 0 后地板降到 6.1%,后来又降到 0%。"

**配对显著性检验**:
> "版本对比不比两个平均分,而是逐题配对看**翻转**:多少题从错变对(b)、从对变错(c)。
> 若真无差别,翻转方向应五五开 → b ~ B(b+c, 0.5),算精确双侧 p 值(McNemar 思路)。
> 好处是只看翻转的题 —— 两版都对/都错的题不携带区分信息,却会稀释平均分。
> **1↑0↓ 时 p=1.0,离显著差得远,而平均分会显示 +3%,很容易自欺。**"

**最诚实的一击**:
> "首轮我报的是 78.8%,后来发现**是我的判分错了**,agent 一行没改。
> 追问词表里我本想写全角问号、实际写成了 ASCII,而模型输出的是全角 —— 三道题全误判。
> 修完用同一批轨迹**离线重判**得 97.0%。
> 所以我把'改了判分就重判历史轨迹'做成了一等操作,并且给判分逻辑本身写了 46 个测试 ——
> **评测代码出 bug 是最坏的,它让所有版本的分数一起偏,你还没有第二把尺子去量这把尺子。**"

### 链 8:并发与容量 —— 三道闸门 + 连接数

**项目点**:有界线程池 8 并发 + 16 排队,超出 503。

**会被拉出的八股**:线程池参数、拒绝策略、GIL、连接池、雪崩/熔断。

**怎么答**:
> "原本我用裸 `threading.Thread`,**没有上限** —— 100 个用户同时提问就起 100 个线程,
> 连接池排满、100 个并发 LLM 调用把账单和上游限流一起打爆。系统会**雪崩而不是降级**。
> 改成有界线程池,超出直接 503 明确告诉用户'现在忙',而不是让他排一个看不到头的队。"

**为什么用线程不用 asyncio**:
> "agent 调用链(模型、Milvus、树模型)全是同步阻塞的,放进事件循环会把整个 worker 卡死。
> GIL 在这里不是问题 —— 我们等的是网络和磁盘 IO,**等待时 GIL 是释放的**。"

**最后一击(连接数算式)**:
> "每 worker ≈ SQLAlchemy 池(10+10) + checkpointer 池(10) = 30 条,
> PG 默认 max_connections=100 → **最多约 3 个 worker**。
> 起更多 worker 前必须同步调大 max_connections,否则新 worker 拿不到连接、请求直接失败 ——
> 这是扩容时最容易踩的坑。
> 另外 `MAX_CONCURRENT_RUNS=8` 是**每 worker** 的,2 个 worker 全局就是 16。"

**为什么容量计数在内存、配额计数在 Redis**(这题很能体现理解深度):
> "判断规则:**你数的东西属于谁,就存在谁那一层。**
> `_inflight` 数的是本进程线程池还剩几个位子 —— 线程池本来就每进程一个,天生私有;
> 配额数的是用户今天花了多少钱 —— 用户的请求会落到任何 worker,必须共用一本账。"

## 三·五、如果换成自部署模型,哪些结论会变(这题很能显判断力)

换模型本身是**改配置不改代码**:vLLM / SGLang 暴露 OpenAI 兼容接口,
`config.yaml` 里改 `base_url` 和 `class` 两行即可(`create_model` 用 importlib 动态加载)。

但**四件事的理由会变**:

| | API | 自部署 |
| --- | --- | --- |
| 成本模型 | 按 token 付费,边际成本 | GPU 租金,固定成本 |
| 省 token 的价值 | 直接省钱 | **大幅下降**,GPU 闲着也烧钱 |
| 配额的意义 | 护钱包 | 变成**公平性**:防一个人占满 GPU 队列 |
| 并发上限依据 | 怕打爆账单和上游限流 | **反过来** —— vLLM 用 continuous batching,并发越高吞吐越高 |

最关键的一条:
> "`MAX_CONCURRENT_RUNS=8` 的理由绑死在'走外部 API'这个前提上。
> 自部署下把 app 层死卡在 8 会让 GPU 大量闲置 ——
> 正确形状是**让推理服务器自己排队**(它比应用层会调度),
> app 层的闸门从'限并发'改成'限排队深度 + 超时'。
> 重试策略也要改:API 的 503 是别人限流,退避重试是对的;
> 自部署的排队超时是自己容量不够,重试只会让队列更长。"

**真正不变的约束只有一条**:PG 的 max_connections。

## 三·六、压测:瓶颈在哪(这条别人几乎都没有)

### 结果

64 核机器、容器限 4GB,压闸门+DB 路径(不打模型):

```
worker=2   1.07 GiB   457 req/s   p99   110ms
worker=4   2.09 GiB   630 req/s   p99   130ms   ← 最优
worker=8   ~4   GiB   341 req/s   p99  2266ms   ← 撞内存顶,开始抖
worker=16  4/4  GiB    42 req/s   p99 53428ms   ← 雪崩
```

### 三个被推翻的猜测(这才是压测的价值)

**① 猜"瓶颈是数据库" → 错。** 压测中 PG 只有 **1 个 active 连接、32 个 idle**。
数据库闲得很。

**② 猜"瓶颈是 CPU" → 错。** 机器 64 核,大量闲置。

**③ 真正的瓶颈是【内存】。** 每个 worker 要各自加载一份嵌入模型 + 三个树模型,
实测约 **520MB/worker**(线性)。4GB 上限 → 最多 ~7 个。

### 这条经验对 AI 服务是普适的

> **worker 数不能按 CPU 核数拍,它是内存约束,不是 CPU 约束。**
> 普通 Web 服务照"核数×2"配 worker 没问题;AI 服务这么配会在启动阶段就把机器打死 ——
> 我实测 16 个 worker 时 p99 是 53 秒。
>
> 想再往上扩,正解不是加内存,是**把嵌入模型抽成独立服务**,让所有 worker
> 共享一份而不是各存一份。那之后 worker 数才回到 CPU 约束。

### 还纠正了我自己写错的文档

原来 engine.py 里按"每 worker 满池 30 条连接"推算,得出"最多 3~4 个 worker"。
压测实测 4 个 worker 只用了 **54/100** 连接 —— 因为 SQLAlchemy 连接池是**懒建**的,
`pool_size=10` 是"最多留 10 条空闲",不是"启动就占 10 条"。
那个算式是**最坏情况上界**,当扩容红线用会白白限制住本可以加的 worker。

### 对应面经题「Python GIL 在 AI Agent 高并发下的影响」

> "我压过。**我们的瓶颈根本不是 GIL,是内存** —— 加 worker 数确实能提吞吐
> (2→4 是 +38%),说明 GIL 确实限制了单进程;但加到 8 就撞内存顶、16 直接雪崩。
> 所以规避 GIL 的标准手段(多进程)在 AI 服务里会先撞上另一堵墙。"

## 四、边界:没做的 + 为什么(敢说这个是加分项)

- **没上真实流量**:单机验证,没接公网用户。→ 直说,别编。
- **HTTPS 没开**:需要域名和证书,配置模板已备好。
- **没有监控告警**:有结构化日志 + request_id + 健康检查端点,但没有 Prometheus/拨测。
  单机无监控系统的情况下判断是 YAGNI。
- **没用消息队列**:知道触发条件(独立扩容 / 任务变长)。
- **没做 Supervisor 之外的多 Agent 模式**:Hierarchical / Swarm 知道是什么,场景没到。
- **LLM-as-a-Judge 刻意不用作主指标**:理由见链 7。
- **限流/配额的数值没有数据支撑**:20 次/分 + 200 次/天是保守默认值。
  注意 20/分钟人根本够不到(一次回答 17.7 秒,手动最多 3.4 次/分)——
  它拦的是脚本不是人;而 200/天对重度用户偏紧,该按真实用量调。
- **rf02 仍失败**:被问"部级认证材料"时不主动纠正错误前提,是当前唯一稳定失败的用例。

## 五、最容易被追问到哑口的五个问题(重点练)

1. "你这个评测集只有 33 题,统计上说明得了什么问题?"
   → 说明不了单点改善(1 次翻转 p 恒为 1.0)。**这是评测集功效不足,不是没有效果。**
     要证明单点改善得给高风险类别加题到 5 道以上。

2. "限流用的什么算法?固定窗口有临界问题知道吗?"
   → slowapi 默认固定窗口。临界问题:第 59 秒打 20 次 + 第 61 秒打 20 次 = 2 秒内 40 次。
     **我们能接受**,因为后面还有容量闸门兜底。要根治得换滑动窗口或令牌桶。

3. "PG 和 Milvus 的数据一致性怎么保证?"
   → 我们的分工是"**PG 是数据源,Milvus 是可重建的索引**"。不追求强一致:
     Milvus 挂了重建即可(几十分钟),所以备份只备 PG 不备 Milvus。

4. "你说 agent 断线不丢,那如果服务器整个断电呢?"
   → 那条 run 就是孤儿。靠启动时 `reap_stale()` 标记失败并给用户看得懂的原因。
     **要做到"断电也不丢"必须上消息队列做任务持久化**,那是下一个规模等级的方案。

5. "最近学了什么?怎么判断值不值得引入生产?"
   → 讲那次提示词改动:我加了三条规则,**跑评测测出来 0 收益、成本 +14%**,于是裁掉了。
     **判断标准就是能不能测出来** —— 测不出收益的改动不进生产,哪怕它"看起来更合理"。
