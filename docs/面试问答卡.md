# 面试问答卡

一问一答,答案都写到「能背下来」的长度。按面试真实顺序排。

配套的深度版在 [面试准备.md](面试准备.md)(追问链、真实数字、边界)。
**这份用来背,那份用来理解。**

## 一、开场(必问)

**问:介绍一下你的项目。**

我做了一个地膜领域的智能体系统。用户问"新疆尉犁种棉花该用什么配方的降解膜",系统会自己查当地土壤气候、调三个机器学习模型预测性能、检索文献标准,给出带出处的建议。技术上是 LangChain 的 ReAct 循环加中间件链,配混合检索 RAG,有 33 题的评测集和完整部署。

**问:详细说说?**

分三层。知识层:1578 篇文献切成 26 万个块,向量加 BM25 混合检索再重排,Recall@1 从 0.587 提到 0.807。能力层:9 个工具加 2 位专家子 agent,三个预测模型 R² 分别是 0.95、0.877、0.852。工程层:中间件链、异步运行、三道流量闸门、优雅停机、33 题评测、328 个测试、一条命令部署。

**问:为什么做这个?**

地膜是个真实痛点:选错配方要么提前破膜没了保墒效果,要么留在地里污染土壤。而这个决策要同时看土壤、气候、配方、生育期,农户和技术员都没法自己算。

## 二、Agent 基础

**问:什么是 Agent?和普通问答机器人什么区别?**

区别在控制权。普通问答是人排好流程,问一次答一次;Agent 是模型自己决定下一步——要不要调工具、调哪个、调完看结果再决定继续还是收尾。

**问:ReAct 循环怎么转?**

Reason 加 Act。模型先想,决定调哪个工具、什么参数;系统执行工具把结果塞回对话;模型看结果再想下一步。循环到模型不再调工具、直接给答案为止。

**问:模型怎么"调用工具"?它不能执行代码。**

模型只是输出一段结构化的话:"我要调 get_soil_info,参数是尉犁县"。真正执行的是我们的代码,执行完把结果作为消息塞回去。所以工具的名字和描述写得好不好非常关键——模型只能靠这两样判断该用哪个。

**问:怎么保证模型选对工具?**

三件事。描述里写清楚什么时候用、什么时候不用;工具不能太多也不能功能重叠;最后必须用评测来量,我们工具选择的召回率是 1.000。

## 三、中间件(Harness)

**问:你说的中间件链是什么?**

一层层包在模型调用外面的东西,像洋葱。我们有 8 层:注入防护、技能注入、记忆注入、轮次刹车、上下文压缩、模型重试、工具计时、工具错误兜底。列表越靠前包得越外面。

**问:为什么注入防护要放最外面?**

两个理由。安全检查要在花钱之前;更重要的是后面所有组件都得在它保护之下——上下文压缩会把用户原文喂给另一个模型,防护放它后面的话,摘要模型先被攻击了。

**问:为什么工具计时要包在错误处理外面?**

这样失败的调用也能记下耗时。反过来的话异常会冲过计时层,那行记录根本不执行,日志里只有成功的有耗时。而"工具卡了 30 秒才失败"和"瞬间失败"是完全不同的两种病。

**问:为什么说 Model 加 Harness 才等于生产级 Agent?**

光有模型就是个会聊天的 API。Harness 补五件事:安全、上下文管理、成本控制、稳定性、可观测。举个证据:我们评测跑 99 次真实对话,发现 RAG 内部那次模型调用不在重试中间件之下,一次网络抖动整个知识库工具就挂,99 次踩中 6 次。

## 四、异步运行(最值钱的设计)

**问:Agent 要跑几分钟,用户断线了怎么办?**

Agent 不绑 HTTP 请求。收到提问先在数据库建一条运行记录、返回 run_id,agent 丢到后台线程池跑。用户断线只是断了推送流,后台照跑完存库。用户回来拿 run_id 就能查结果。

**问:不这么做会怎样?**

连接一断生成器被取消,agent 半路死掉。三输:钱花了、答案没了、用户还得重问。

**问:数据分别存在哪?**

PostgreSQL 存权威状态和最终答案,不能丢;Redis Stream 存过程事件,TTL 一小时,丢了只影响回放过程不影响答案;后台线程池跑 agent。

**问:为什么事件流不能放进程内存?**

多 worker 部署时,用户刷新后的请求可能落到另一个 worker,内存里的事件它读不到,重连就失败。

**问:服务器重启,跑到一半的怎么办?**

两条兜底。正常停机时主动把在途的标记失败;异常重启靠启动时扫一遍,把超过 15 分钟还是运行中的标记失败——因为线程活在内存里,服务重启过就说明这些都是孤儿。

**问:为什么不用消息队列?**

现在单机几十人、一次 30 秒,进程内有界线程池够用且零额外运维。知道下一步是消息队列,触发条件有两个:要独立扩容 worker,或任务长到重启丢了很心疼。

## 五、流量控制

**问:限流和配额有什么区别?**

限流管速率,配额管总量。只有限流,用户每分钟规矩打 20 次一天两万多次,账单崩了;只有配额,他一秒打完 200 次,服务压垮了。

**问:为什么计数必须放 Redis?**

我们跑多个 worker 进程。计数存进程内存的话每个 worker 各算各的,限额直接乘以 worker 数。

**问:为什么用 INCR 不用读出来加一再写回?**

读改写有竞态:两个 worker 同时读到 99,都写 100,少算一次。INCR 是 Redis 内部一步完成的原子操作。

**问:配额怎么按天重置?**

key 里带日期,`前缀:日期:用户`。新的一天自动是新 key,天然从 0 开始,不需要定时任务清零。

**问:Redis 挂了怎么办?**

直接放行。这道门守的是钱,损失有限;为了防它让整个服务瘫痪代价更大。但如果是鉴权依赖 Redis 就必须反过来,全部拒绝——守数据的门坏了得关门。

**问:并发怎么控制?**

有界线程池,每个 worker 最多同时跑 8 个,再排队 16 个,超出返回 503。原来用的是没有上限的线程,100 人同时提问就起 100 个线程。

## 六、进程与线程

**问:worker 是线程吗?**

不是,是独立进程。进程之间内存完全隔离,所以每个 worker 都要各自加载一份模型——实测每个吃 677MB。

**问:为什么不用线程,那样能共享内存?**

Python 有 GIL,同一进程里同一时刻只有一个线程能执行 Python 代码,开十个线程也跑不满十个核。要利用多核只能开多进程,代价就是内存复制多份。

**问:那为什么 agent 用线程池就够?**

Agent 大部分时间在等——等模型、等数据库、等网络。Python 等 IO 时会释放 GIL,别的线程能跑。所以对"等得多算得少"的活,线程够用。

**问:GIL 在 AI Agent 高并发下有什么影响?**

我压测过。加 worker 数确实能提吞吐,2 到 4 是加了 38%,说明 GIL 确实限制单进程。但加到 8 就撞内存顶,16 直接雪崩,p99 到了 53 秒。所以规避 GIL 的标准手段是多进程,但 AI 服务会先撞上内存这堵墙。

## 七、压测(别人几乎没有)

**问:你这个系统能抗多少并发?**

要分两层说。闸门层不打模型的话实测 630 req/s,p99 130 毫秒;真实 agent 对话是 1.8 req/s,p50 4.6 秒。差 350 倍,因为时间全花在等大模型上,不在我们代码里。

**问:瓶颈在哪?**

压测推翻了我两个猜测。猜数据库——错,压测中 PG 只有 1 个活跃连接 32 个空闲;猜 CPU——错,64 核大量闲置。真瓶颈是内存,每个 worker 要各自加载一份嵌入模型加三个树模型,520MB 起。

**问:那怎么扩?**

正解不是加内存,是把嵌入模型抽成独立服务,让所有 worker 共享一份而不是各存一份。之后 worker 数才回到 CPU 约束。

**问:压测为什么不打真模型?**

打真模型测的是模型厂商的限速和网络,不是我们的系统。所以分两种模式:闸门模式不打模型可以压很高并发,真实模式少量请求校准单题成本。

## 八、RAG

**问:你的 RAG 怎么做的?**

1578 篇文献切成 26 万个块。检索用向量加 BM25 混合、RRF 融合,再用交叉编码器重排。Recall@1 从纯向量的 0.587 到 0.807。

**问:为什么要混合检索?**

向量擅长语义,但精确词会丢——比如国标编号 GB/T 35795,向量可能召不回;BM25 擅长精确词但不懂同义。两个互补。

**问:RRF 是什么?**

倒数排名融合。两路检索各出一个排序,同一个块按它在各路里的名次算 1/(k+名次) 再相加。好处是只用名次不用分数,所以两路的分数量纲不同也能融合。

**问:文档怎么切的?固定长度会截断句子吗?**

我们用 Small-to-Big:检索用子块——短、语义聚焦、命中准;送给模型的是它的父块——长、上下文完整。这解决了"切太碎语义断裂、切太大检索不准"的矛盾。

**问:怎么防幻觉?**

分三层治。没召回到,靠混合检索;召回错了,靠重排;模型乱答,靠强制它只依据检索到的资料、数字和原文一致、每条结论标出处。

**问:召回的文档不是最新的怎么办?**

这个我踩过。用户问"现在 PBAT 多少钱",agent 从知识库翻出 2023 年文档里的价格当成现价答了。我先在系统提示里写"不要把历史价当现价",跑评测测出来完全没用,成本还涨了 14%。后来改成结构性修法:让检索出处带上文献年份,模型看到的不再是一段无时间的事实,而是"某报告(2023 年)"。改完那道题从 0/3 变 3/3。

## 九、评测(最能拉开差距)

**问:怎么科学评测 Agent?新版本怎么证明比旧版本好?**

先量噪声地板:同一个版本重复跑三轮,看它自己抖多少。不知道这个,任何对比都没意义。然后版本对比不比两个平均分,而是逐题配对看翻转——多少题从错变对、多少从对变错,按二项分布算精确 p 值。

**问:为什么不用大模型当裁判打分?**

同一版本跑两次裁判给分能差好几个点,那"新版本加 2%"是真提升还是噪声就没法回答。没法回答的指标等于没有指标。所以主指标全是规则可判的:工具集合匹配、关键点正则、数值容差。

**问:为什么要配对检验而不是比平均分?**

两版都对或都错的题不携带区分信息,却会稀释平均分。只看翻转的题才有信息。而且 1 好 0 坏时 p 值等于 1.0 离显著差得远,但平均分会显示涨了 3%,很容易自欺。

**问:噪声地板量出来多少?**

一开始 12.1%,约等于 4 道题——那把尺子测不出任何小于 4 道题的改进。根因是评测在用一个没设 temperature 的模型,服务端默认是 1。压到 0 之后降到 6.1%,后来到 0%。

**问:temperature 设为 0,输入固定输出就一定完全相同吗?**

不一定。服务端的批处理、MoE 路由都会带来残余抖动。温度 0 只是去掉了最大的那个噪声源——采样,所以噪声地板仍然要实测,不能假设是 0。

**问:评测里发现过什么问题?**

最有意思的是我第一次报的分数是错的。首轮跑出 78.8%,看着像 agent 在追问和拒答上很差。逐题翻轨迹才发现 agent 全答对了,是我的判分错了——追问词表里我本想写全角问号,实际写成了 ASCII,而模型输出的是全角。修完用同一批轨迹离线重判是 97.0%,agent 一行没改。

## 十、多 Agent

**问:你们的多 Agent 怎么协作?**

子 agent 就是一个工具。主 agent 像项目经理,通过一个 delegate 工具把子任务派给专家;专家用自己的窄工具集独立完成,只把结论回给主 agent。官方的 deepagents 包也是这个模式,它那个工具叫 task。

**问:怎么防止无限递归?**

结构上防,不靠提示词。专家的工具集里不含 delegate 工具,所以它想再派活也派不了。

**问:子 agent 之间怎么隔离?**

专家不传 checkpointer,每次调用无状态无残留,也看不到主对话历史。这样专家不背主对话的包袱,主 agent 也不被专家的中间步骤污染。

**问:多个子 agent 能并行吗?**

能,而且是框架白送的——LangGraph 本来就并行执行同一轮的多个工具调用。我实测一轮 3 个各 1 秒的工具总耗时 1.03 秒。但代价是两条 LLM 循环同时跑,并发调用翻倍,这正是容量闸门要存在的理由。

**问:为什么只有两位专家?**

子 agent 只在三种情况下划算:内部要转很多圈、需要更窄权限、能用更便宜模型。反例是"用量计算专家"——那个工具一次调用就出结果,套一层子 agent 反而多付一整条 LLM 循环。而且每加一位专家,主 agent 派错的概率就上升。

**问:子 agent 的运行状态你们记录吗?**

记。每次委派有独立 id,记录派给谁、内部调了哪些工具、花了多少 token、多久、成功与否,失败也记。这块是我对照 deepagents 审出来的——原来只返回一个字符串,子 agent 烧的 token 完全不计入成本统计,内部调用全是黑箱。

## 十一、记忆

**问:你们的长期记忆和短期记忆怎么实现的?**

短期是滑动窗口加摘要压缩,只在一次会话内有效。长期是跨会话的:一次运行结束后异步从对话里抽取事实,存进数据库同时向量化,下次这个用户提问时按语义召回相关的注入进去。

**问:为什么需要长期记忆?**

用户上周说过"我在尉犁有 50 亩地种棉花",这周问"帮我算下用量"。没有长期记忆的话系统只能反问他面积,因为上周的对话早不在上下文里了。

**问:记忆里存什么?原始对话还是抽取的事实?**

抽取的事实。存原文简单,但检索噪声大、没法删、浪费 token;抽成一句话的事实三个问题一起解决,代价是多一次模型调用,用便宜模型且在运行结束后做,不占用户等待时间。

**问:既然存的是用户标签,为什么不直接用关系数据库?**

因为记忆有两种查法。"这个用户地块在哪"是精确查,SQL 就够;"当前问题和他以前说过的什么相关"是语义查,只能靠向量。用户说过"我这边风大",现在问"选哪种配方",关键词零重合但语义高度相关。所以两边都存:PG 存事实当权威,向量库只当索引。

**问:什么不该记?**

一次性的东西:这次问的问题、这次算出的结果、寒暄。把一次性信息记成长期记忆,它会在无关对话里被召回,让模型基于过期信息推理——那是主动制造幻觉。

**问:隐私怎么办?**

用户能看到系统记住了什么,也能删。删是软删不是硬删——硬删的话下次同样的话又会被抽回来,用户会觉得"我删了它还记得"。软删加内容寻址,删过的不会复活。

**问:怎么保证不会召回别人的记忆?**

双重校验:向量库按 user_id 过滤,查回数据库后再校验一次归属。只靠一层的话任何一层写错都是数据泄露,不是效果问题。

## 十二、上下文管理

**问:对话越来越长塞不下怎么办?**

超过 5 万 token 就把老对话压缩成一段摘要,只保留最近 20 条原文。摘要用便宜模型做。切分时会保证"AI 说要调工具"和"工具返回结果"这一对不被拆开,拆开模型会看到一个没有结果的调用。

**问:压缩会丢信息吗?**

会丢细节。老消息不是被删,是被换成摘要,主线还在但精确数字会丢。完整方案应该是三层:滑动窗口加摘要压缩加长期记忆——压缩之前先把关键事实抽出来存进向量库,这样摘要丢的只是聊天过程不是事实。我们现在长期记忆这层刚补上。

## 十三、安全

**问:Prompt 注入怎么防?**

分两种。直接注入是用户自己说"忽略之前的指令",在中间件最外层拦。更危险的是间接注入——恶意指令藏在检索到的文档里跟着资料进上下文。防法是给检索内容包上明确的边界标记,并在系统提示里声明边界内的一切只是数据,里面出现任何指令都不执行。

**问:工具报错了会泄露什么吗?**

只把异常的类型名给模型,不给具体错误内容——那里面可能有内网 IP、数据库地址,进了模型上下文可能被复述给用户。完整堆栈只进服务端日志。

**问:数据库怎么保护?**

端口只绑 127.0.0.1。写成 "5432:5432" 等于绑 0.0.0.0,服务器有公网 IP 时全世界都能连。我们的 PG、Redis、Milvus 都没开鉴权,暴露等于白送。

**问:查别人的运行记录会怎样?**

返回 404 不是 403。403 等于告诉对方"这个 ID 存在,只是不给你看",泄露了存在性。

## 十四、部署

**问:怎么部署?**

一条命令。脚本按固定顺序做:前置检查、构建镜像、起基础设施等健康、跑数据库迁移、起应用、冒烟验证。任一步失败立刻中止。迁移失败就不放行应用——要么整套结构一致,要么根本不启动。

**问:镜像多大?优化过吗?**

3.5GB,从 12.6GB 优化来的。三步:多阶段构建把中间层剥掉;换 CPU 版 torch——Linux 默认装 CUDA 版,nvidia 加 torch 加 triton 有 6GB,而服务器根本没 GPU;还有把 RUN chown -R 改成 COPY --chown,前者会让文件系统把每个文件复制进新层,2.4GB 存了两遍。

**问:部署踩过什么坑?**

最典型的是优雅停机一次都没执行过。我写好了停机代码,日志里却连一句 Shutting down 都没有——因为容器里 PID 1 是 sh,shell 不转发 SIGTERM,uvicorn 根本没收到信号,宽限期一到直接被强杀。加 exec 让 uvicorn 自己成为 PID 1 才生效。代码写得再对,信号进不来就等于没写。

**问:还有别的吗?**

.dockerignore 只支持整行注释,我写了行尾注释,那些规则全部静默失效——包括保护 .env 的那两条,结果 API 密钥进了镜像。还有一次是运行时要读的数据文件被整个目录排除了,构建成功、健康检查全绿、容器状态正常,但用户直接看到 FileNotFoundError,一路漏到了用户面前。

## 十五、技术选型与对比

**问:为什么用 LangGraph 不自研?**

ReAct 循环、状态持久化、中间件、并行工具调用这些都是通用能力,自研要重造一遍还不如它稳。我们把精力放在领域上:混合检索、领域预测模型、评测体系。

**问:和字节的 deer-flow 比呢?**

底座一样,深度不同。同版本的 LangChain create_agent、同样的中间件链、子 agent、MCP、skills。它是通用平台所以中间件多得多、有沙箱、有多模态、接了五个 IM 渠道;我们是垂直领域,在它没做的两块上更深:混合检索 RAG——它依赖里连向量库都没有,和可量化的评测体系。

**问:你从它那里学到什么?**

我对照它审过自己的实现。它有个 delegation_ledger 中间件专门记录每次委派,我们原来没有,子 agent 的 token 完全没计入成本统计。发现后补上了。

## 十六、最容易被问倒的

**问:你这评测集只有 33 题,统计上说明得了什么?**

说明不了单点改善——1 次翻转的双侧 p 值恒为 1.0。这是评测集功效不足,不是没有效果。要证明单点改善得给高风险类别加题到 5 道以上。

**问:限流用什么算法?固定窗口的临界问题知道吗?**

我们用的固定窗口。临界问题是第 59 秒打 20 次加第 61 秒打 20 次,2 秒内 40 次。我们能接受,因为后面还有容量闸门兜底。要根治得换滑动窗口或令牌桶。

**问:PG 和向量库的数据一致性怎么保证?**

我们不追求强一致。分工是 PG 是数据源、向量库是可重建的索引,向量库挂了重建即可,所以备份只备 PG。写入时先写 PG 再写向量,反过来的话 PG 失败会留下孤儿向量。

**问:断电了呢?**

那条运行就是孤儿,靠启动时扫描标记失败。要做到断电也不丢,必须上消息队列做任务持久化,那是下一个规模等级的方案。

**问:最近学了什么?怎么判断值不值得引入生产?**

讲那次提示词改动。我加了三条规则,跑评测测出来零收益、成本涨 14%,于是裁掉了。判断标准就是能不能测出来——测不出收益的改动不进生产,哪怕它看起来更合理。
