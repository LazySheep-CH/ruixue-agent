# 检索优化记录

本文件记录地膜 RAG 检索层的优化过程:每一步的**问题 → 方法 → 数据 → 结论 → 是否落地**。
评测集为 `data/eval/evalset.jsonl`(338 题,多标注 + relevance,冻结),评测口径见
[评测方法.md](评测方法.md)。核心指标 **Recall@k / MRR**(下游是大模型读 top-k,
这两个直接决定"有没有对的料、最相关的靠不靠前")。

---

## Step 0 · 三层基线

**目的**:逐层量化每个检索组件的增益,每层"开 vs 不开只差一个参数",增量可信。

| 配置 | R@1 | R@3 | R@10 | MRR |
| --- | --- | --- | --- | --- |
| 纯向量 | 0.379 | 0.545 | 0.697 | 0.479 |
| + BM25(混合 RRF) | 0.438 | 0.617 | 0.714 | 0.535 |
| + rerank(cross-encoder) | 0.628 | 0.738 | 0.817 | 0.693 |

*(单标注口径,Step 2 会修正)*

**结论**:BM25 改善召回(R@3 +0.072),rerank 改善精排(R@3 +0.193,贡献最大)。
三层都保留为上线管线。

---

## Step 1 · 查询改写(带闸门)

**问题**:分策略诊断发现 **user 口语题 R@3 只有 0.480**,远低于 fact(0.90)。根因是
一线用户说大白话("浇点水管用不"),与文献术语存在**词汇鸿沟**,现役 embedding
(bge-small-zh)对口语弱。真实 agent 走 RAG 前本就会先改写用户 query,故把改写作为
检索前的标准预处理层。

**方法**:两段式**带闸门**改写器(`ruixue_agent/rag/query_rewrite.py`)——① 闸门先判
"口语/规范",术语题**原样放过**(避免把精确措辞改乱)② 只对口语题术语化。
教训:早前无闸门直接全量改写,伤 fact −0.05、multihop −0.22;解耦闸门后修复。

**数据**(338 题):

| | 结果 |
| --- | --- |
| 闸门决策 | user 改 73/100;**fact 0/142、multihop 0/48 零误伤** |
| 总体 R@3(单标注) | 0.738 → 0.766 |
| user R@3(单标注) | 0.480 → 0.540(**+0.060**) |
| fact / multihop | 零副作用,微涨 |

**当时结论**:单标注下净赚、零副作用,遂接入 `Retriever(rewriter=…)`(检索用改写 query、
rerank 用原始 query)。

**⚠️ 经 Step 2 多标注复核后修正(重要)**:在多标注(更真实)尺子下,**无重写反而略高**——
R@3 0.910 vs 0.897、user 0.840 vs 0.830。归因:pooling 建池用的是【原始问题】,候选池
偏向"原始问题能检索到的块";带重写检索到**池外**的有效块被判未命中,**评测对改写不公平**。
加上改写收益本就小(+0.06)、每查询要多调一次 LLM(有成本)。
**决策:默认关闭改写。** `Retriever` 的 `rewriter` 参数**保留作可选、不删**,用 `run_eval
--rewrite` 可随时复测。要严格评估改写需重建"把改写路径也纳入建池"的公平尺子,但无重写
已达标、优先级低,暂不做。

## Step 2 · 多标注 pooling + relevance 分级

**问题**:评测用**单标注**(每题 1 个 gold),但库里 26 万块,一个问题(尤其口语题)常有
多篇能答。检索找到另一篇有效块却被判未命中 → **系统性低估 Recall**。这是标注口径缺陷,
不是检索差。多标注是企业/微软/RAGAS 检索评测的前提。

**方法**(`scripts/pool_evalset.py`):TREC 式 pooling——多路建池(向量+BM25,不同原理都
进池)+ **LLM 严格 judge**(relevance 0-3,"能答出那个具体点"才 ≥2,"只是同话题"给 1)。
教训:早前用本地 reranker 当 judge,它把"同话题"给 0.9+,过度标注刷虚高;换严格 LLM
judge 后收敛。gold(算 Recall)= relevance≥2。

**数据**:平均每题补到 **3.46 个 gold**(fact 3.04 < multihop 3.48 < **user 4.06**,
印证口语题被冤枉最狠);单 gold 的题从 290 降到 59。**同一检索结果,两把尺子对照**:

| 尺子 | R@3 | R@10 | MRR |
| --- | --- | --- | --- |
| 单标注(旧) | 0.766 | 0.848 | 0.708 |
| **多标注(新)** | **0.903** | **0.976** | **0.835** |

user 单标注 0.540 → 多标注 **0.830**。检索一个字节没变,分数上升 100% 来自标注修正
(非灌水:judge 严格、平均只补 3.46 个、留了 `evalset_singlelabel.jsonl` 可复核)。

**结论**:`evalset.jsonl` 升级为多标注(唯一真相),`evalset_singlelabel.jsonl` 留档对照。
修正后对照企业标准:**Recall@5 0.924 / Recall@10 0.976 / MRR 0.835 均达上线线**。

## Step 3 · fanout 诊断(候选数 vs 排序)

**问题**:引入 nDCG 后发现 nDCG@10 只有 0.673(企业通用线 0.85)。诊断"是候选噪声还是
rerank 模型上限"。当时 rerank 一次要在 ~84 个候选里排序,怀疑噪声淹没精排。

**方法**:固定管线,只扫 fanout(喂给 rerank 的候选数)。

| fanout | rerank 候选 | R@10 | MRR | nDCG@10 |
| --- | --- | --- | --- | --- |
| 1 | 18 | 0.924 | 0.820 | 0.716 |
| **2** | **35** | **0.966** | **0.834** | 0.703 |
| 3 | 52 | 0.962 | 0.827 | 0.685 |
| 5 | 84 | 0.976 | 0.835 | 0.673 |
| 8 | 131 | 0.972 | 0.826 | 0.657 |

**结论**:
- **候选越多 nDCG 越低**——"候选噪声淹没 rerank"假设坐实。
- fanout=1 nDCG 最高但 **Recall@10 掉到 0.924**(候选太少,高相关块没进 rerank),不选。
- **fanout=2 是甜点**:候选 84→35,去掉一半噪声,**Recall/MRR 几乎不掉、rerank 计算省近一半**。
  **已落地**(`retriever.py` _FANOUT=2),理由是省成本 + 更干净,不是为 nDCG。
- **nDCG 不再作为目标**:下游是大模型**全读 top-k**,不在乎相关块内部精确排序,nDCG 业务
  权重低;真正决定成败的 Recall/MRR 已达标。0.85 是拍脑袋的通用线,不适配本任务。nDCG
  从评测中移除。

## 当前上线管线与真实基线

**管线**:向量 + BM25(RRF)→ rerank(fanout=2)。**默认不含查询改写**(见 Step 1 修正——
多标注下无净收益且评测对它不公平;`rewriter` 参数保留作可选)。
**真实基线**(多标注,338 题,`run_eval`):**R@1 0.769 / R@3 0.910 / R@5 0.952 /
R@10 0.979 / MRR 0.849**,分策略 R@3 fact 0.965 / multihop 0.896 / user 0.840。
检索层达标(Recall@5/10、MRR 均超企业上线线)。

**后续可做**(按业务价值,非 nDCG):接 agent 后的生成层评估(Faithfulness / 引用正确 /
拒答)、红线(数值/标准号/引用零错)、user 题闸门召回、真实日志回流 hard set。
