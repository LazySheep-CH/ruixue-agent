# 运维手册

面向**真实上线**的日常操作。每一项都已实测验证,不是纸面流程。

## 部署

### 一条命令

```bash
bash scripts/ops/deploy.sh
```

脚本按固定顺序做六件事,任一步失败立刻中止:

```
前置检查 → 构建镜像 → 起基础设施(等健康)→ 跑迁移 → 起应用 → 冒烟验证
```

**为什么要脚本而不是手敲 `docker compose up`**:部署是最容易出错又最不能出错的
一步。手敲会漏 `-f prod.yml`、会忘了跑迁移、会在健康检查还没过时就宣布上线。

### 首次部署要准备什么

```bash
cp docker/.env.prod.example docker/.env.prod   # 然后填 DEEPSEEK_API_KEY / JWT_SECRET
uv run python scripts/train/train.py all       # 生成 models/predictors/**
```

`JWT_SECRET` 必须换成随机值 —— 用默认值等于任何人都能伪造登录态。deploy.sh 会拦。

**构建机必须能拉到基础镜像。** 国内机器常连不通 Docker Hub / ghcr.io
(本机实测两者都 EOF 失败),表现为构建卡在第一行 `FROM`。配镜像加速器:

```json
// /etc/docker/daemon.json,改完 systemctl restart docker
{ "registry-mirrors": ["https://docker.m.daocloud.io"] }
```

基础镜像已从 `ghcr.io/astral-sh/uv` 换成 Docker Hub 的 `python:3.11-slim-bookworm`
+ pip 装 uv,就是因为 ghcr.io 更难连。**基础镜像必须来自构建机确实能访问的仓库**,
这不是风格问题 —— 拉不下来就是整条部署链断在第一步。

嵌入模型同理:构建机连不上 HuggingFace 时加
`--build-arg HF_ENDPOINT=https://hf-mirror.com`。

### 服务拓扑

```
        公网
          │  80 / 443
      ┌───▼───┐
      │ nginx │  唯一入口:TLS 终结、同源合并、SSE 直通
      └─┬───┬─┘
   /api │   │ /
    ┌───▼┐ ┌▼────┐
    │app │ │ web │   两者都【不映射宿主机端口】,只能经 nginx 访问
    └─┬──┘ └─────┘
      │
  ┌───┴────┬────────┬─────────┐
  ▼        ▼        ▼         ▼
postgres  redis   milvus  (etcd+minio)   全部只绑 127.0.0.1
```

**为什么 app 不暴露端口**:直连就绕过了 nginx 上的 TLS、超时和请求体限制。
**为什么数据库只绑回环**:`"5432:5432"` 是绑 `0.0.0.0` —— 服务器有公网 IP 时,
全世界都能连你的库。PG/Redis/Milvus 在本项目里都没开鉴权,暴露 = 白送。

### 编排文件怎么组合

```bash
docker compose -f docker/docker-compose.yml -f docker/docker-compose.prod.yml <命令>
```

`docker-compose.yml` = 基础设施(开发/生产共用),`docker-compose.prod.yml` = 叠加层,
只写差异(migrate / app / web / nginx)。**不复制成两份完整文件** —— 复制出来的两份
一定会慢慢跑偏,迟早出现"开发能跑、生产起不来"。

### 已实测跑通(2026-08-07)

第一次把整条链路真跑了一遍,而不是只写编排文件:

```
bash scripts/ops/deploy.sh
  ▶ 前置检查 → ✓ 配置与模型产物齐备
  ▶ 构建镜像 → ✓
  ▶ 启动基础设施 → ✓ 依赖已就绪
  ▶ 执行数据库迁移 → alembic upgrade head ✓
  ▶ 启动应用(app / web / nginx)→ ✓
  ▶ 冒烟验证 → ✓ /api/health/ready · ✓ 前端页面可访问
  ▶ 部署完成 → http://127.0.0.1:80
```

经 nginx 的真实验证:

| 验证项 | 结果 |
| --- | --- |
| 无 key / 错 key | 401 ✓ |
| 真实对话 `POST /api/chat` | 「1 公顷 = 15 亩」✓ |
| SSE 流式 | run_id 先到,随后 token 逐条到达 ✓(证明 `proxy_buffering off` 生效) |
| 优雅停机(在途运行时 `docker stop`) | 在途运行被排空;超时的那条立刻落库 `failed`,error =「服务重启,本次运行未能完成,请重新提问」✓ |

**镜像 12.6GB → 3.51GB**(见下)。

### 真跑一遍才暴露的七个问题

这些全都是"看代码看不出来、只有真部署才会炸"的类型:

| # | 问题 | 根因 |
| --- | --- | --- |
| 1 | 构建上下文 5.65GB,且**密钥进了镜像** | `.dockerignore` 只支持整行注释,写了行尾注释的规则(含 `.env`、`config/config.yaml`)全部静默失效 |
| 2 | 镜像 12.6GB | Linux 默认装 CUDA 版 torch(nvidia 3.6G + torch 1.7G + triton 691M),而服务器没 GPU |
| 3 | 又多 4GB | `RUN chown -R` 会把每个文件复制进新层 → 2.4GB 存两遍。改用 `COPY --chown` |
| 4 | 烤模型步骤失败 | `uv run --no-project` 的语义正是"忽略本项目环境" |
| 5 | HF 下载报 `UnsupportedProtocol` | `HF_ENDPOINT=""` —— **空字符串 ≠ 未设置** |
| 6 | 容器里找不到预测模型 | 目录是 `DR/WVTR/TS`,我写成小写。Windows 不区分大小写所以本机自查通过,Linux 容器区分 |
| 7 | **优雅停机一次都没执行过** | PID 1 是 `sh`,shell 不转发 SIGTERM → uvicorn 收不到信号 → 宽限期一到直接 SIGKILL。加 `exec` 才让 uvicorn 成为 PID 1 |

第 7 个最值得记:代码写得再对,信号进不来就等于没写。**日志里连一句 `Shutting down` 都没有** 才是唯一能发现它的线索。

### 环境变量写在哪个文件里(这里错了会静默失效)

```
docker/.env        compose 的 ${VAR} 插值来源 → 端口、镜像标签、worker 数
docker/.env.prod   env_file,只影响【容器内部】 → API Key、JWT_SECRET、配额
```

把 `HTTP_PORT` 写进 `.env.prod` 不会改变任何端口映射,却会让人以为改了。
`deploy.sh` 现在会主动检查并拦下这种写错位置。

### 三个部署期特有的坑(已在代码里堵死)

| 坑 | 后果 | 怎么堵的 |
| --- | --- | --- |
| 代码里写死 `localhost` | 容器里的 localhost 是容器自己 → 连不上 PG/Milvus | `POSTGRES_HOST` / `MILVUS_URI` 环境变量,默认仍是 localhost 不影响本机开发 |
| `models/` 被 gitignore | 新机器 clone 后没有预测模型,三个预测工具全 FileNotFoundError | 镜像在有产物的机器上构建,**Dockerfile 里加构建期断言**,缺产物直接构建失败 |
| 嵌入模型运行时从 HF 下载 | 冷启动拉 100MB;国内机器连不上 HF 就起不来 | 构建期烤进镜像,运行期 `HF_HUB_OFFLINE=1` 强制离线 |

原则都是同一个:**能在构建期失败的,绝不留到线上失败。**

### nginx 上两个必须知道的配置

**① SSE 三件套**(`proxy_buffering off` + `X-Accel-Buffering: no` + 长 `read_timeout`)

nginx 默认会把上游响应攒够一块再发。对普通 JSON 是优化,对 SSE 是灾难:用户盯着
转圈几十秒,然后答案唰一下全出来 —— **流式输出白做了**。而 `read_timeout` 默认 60s
会把还在生成的 agent 连接直接掐断。

**② upstream 用变量 + resolver,不用 `upstream` 块**

nginx 在**启动时**把主机名解析成 IP 并一直用它。容器一重建 IP 就变,nginx 还在打
旧地址 —— 502 且不会自愈,非重启 nginx 不可。写成 `set $backend "app:8000"` 配
`resolver 127.0.0.11 valid=10s`,就变成按 TTL 重新解析。代价是失去上游 keepalive,
这个量级下不值一提。

### HTTPS

需要你自己的域名和证书,所以没写死在配置里。步骤见
`docker/nginx/conf.d/app.conf` 末尾;模板在同目录 `app-tls.conf.example`。
证书 90 天到期,**记得加 crontab 每月 `certbot renew`**。

### 升级与回滚

```bash
APP_TAG=v0.3.2 bash scripts/ops/deploy.sh    # 升级
APP_TAG=v0.3.1 bash scripts/ops/deploy.sh    # 回滚:换个标签重跑
```

生产**不要用 `latest`** —— 出问题时无法确定线上跑的到底是哪个版本,也没法回滚。

⚠ 回滚只回代码,**不回数据库**。迁移要尽量向后兼容(加列而不是改列),
否则新版建的表结构会让旧版代码报错。

## 备份与恢复

### 备份什么、为什么

| 数据 | 在哪 | 丢了会怎样 | 策略 |
| --- | --- | --- | --- |
| 用户账号、对话历史 | PostgreSQL | **不可恢复** | 必须备份 |
| 文档正文、分块、BM25 词频 | PostgreSQL | 重跑 MinerU 解析要 5 小时+ | 必须备份 |
| 向量索引(22.3 万条) | Milvus | 可从 PG 正文重算(几十分钟) | **不备份**,靠重建 |

**原则:数据是资产,索引是派生物。** 能用代码重新生成的就不占备份空间。

### 日常备份

```bash
bash scripts/ops/backup.sh
# → backups/ruixue_20260806_060756.dump(实测 1025MB 库 → 158MB)
# 自动做结构校验;保留 14 天(KEEP_DAYS 可调)
```

**生产必做两件事**(否则等于没备份):
1. 加进 crontab,每日自动跑:`0 3 * * * cd /path/to/repo && bash scripts/ops/backup.sh`
2. 把 `backups/` **同步到另一台机器或对象存储** —— 备份和数据库在同一块盘上,盘坏了一起没。

### 恢复演练(每季度至少做一次)

**没验证过恢复的备份,不算备份。** 恢复到独立的演练库,不碰生产:

```bash
CONFIRM=yes RESTORE_DB=ruixue_verify bash scripts/ops/restore.sh backups/<文件>
```

核对行数时**必须用 `count(*)`,不能看 `pg_stat_user_tables`** —— 后者是统计估算值,
会显示不一致把人吓一跳(实测踩过:估算 251487 vs 真实 262782)。

```sql
SELECT count(*) FROM chunks;   -- 和生产库逐表对比
```

演练完删掉:`docker exec rxmvp-postgres dropdb -U ruixue ruixue_verify`

**最近一次演练结果**:chunks 262782 / documents 1578 / users 54 / term_df 255089,
与生产库**逐表完全一致** ✅

### 真出事时的恢复顺序

```bash
# 1. 停服务(避免恢复过程中有写入)
# 2. 恢复 PG
CONFIRM=yes bash scripts/ops/restore.sh backups/<最近一份>
# 3. 重建向量索引(PG 正文还在,重算即可)
uv run python scripts/load_milvus.py
# 4. 起服务,验证 /health/ready 返回 ready
```

## 异步运行(Run)机制

### 解决的问题

原先 agent 直接跑在 SSE 请求里:客户端一断(刷新页面、切网络、手机锁屏),
生成器被取消 → agent 半路停下 → **钱花了、结果没有、用户还得重问**。

现在:

```
POST /chat/stream  → 创建 Run(PG)→ 后台线程跑 agent(不绑请求生命周期)
                   → 事件写 Redis Stream → SSE 从 Stream 读并推给客户端
```

客户端断开只是断了这条 SSE,**agent 继续跑完并落库**。

### 相关端点

| 端点 | 用途 |
| --- | --- |
| `POST /chat/stream` | 发起对话。流的**第一个事件**是 `{"type":"run","run_id":...}`,客户端应存下 |
| `GET /chat/runs/{run_id}` | 查状态与结果(刷新页面后用) |
| `GET /chat/runs/{run_id}/stream` | 重连:从头补发事件并继续推 |

三者都做**归属校验** —— 拿别人的 run_id 只会得到 404(不用 403,避免泄露"这个 run 存在")。

### 职责边界

```
PostgreSQL(runs 表)= 权威状态,持久;重启后靠它识别残留
Redis Stream        = 事件缓存,TTL 1 小时;丢了只影响"回放过程",不影响最终答案
```

事件流必须放 Redis **而不是进程内存**:多 worker 部署时,用户刷新后的请求可能落到
另一个 worker,内存里的事件它读不到。

### 残留清理

执行是进程内的后台线程。进程被 kill / 机器重启时,线程没了但库里还写着 `running`,
用户会一直等一个永不完成的运行。**服务启动时自动调 `reap_stale()`**,把超过 15 分钟
仍 running 的标记为失败,并给出用户看得懂的原因。

排查时可直接查:
```sql
SELECT run_id, status, created_at, error FROM runs ORDER BY created_at DESC LIMIT 20;
```

## 并发与容量

### 三道闸门,各管一段

| 闸门 | 管什么 | 默认 | 超了怎样 |
| --- | --- | --- | --- |
| 限流 `20/minute` | 单用户**频率** | 20 次/分 | 429 |
| 配额 `DAILY_CHAT_QUOTA` | 单用户**每日总量** | 200 次/天 | 429 |
| 容量 `MAX_CONCURRENT_RUNS` | **全局同时在跑**的 agent 数 | 8(+16 排队) | 503 |

前两道防"单个用户滥用",第三道防"整体过载"—— 缺了第三道,100 人同时提问会起
100 个线程,连接池排满、并发 LLM 调用把账单和上游限流一起打爆。

### 连接数怎么算(扩容前必看)

```
每个 worker ≈ SQLAlchemy 池(10 + 10 overflow)+ checkpointer 池(10)= 30 条
PostgreSQL 默认 max_connections = 100
        → 最多约 3 个 worker
```

**起更多 worker 前必须同步调大 PG 的 `max_connections`**,否则新 worker 拿不到连接、
请求直接失败 —— 这是扩容时最容易踩的坑。

相关环境变量:`DB_POOL_SIZE` / `DB_MAX_OVERFLOW` / `CHECKPOINTER_POOL_SIZE`
/ `MAX_CONCURRENT_RUNS` / `MAX_QUEUED_RUNS`。

### 排查"突然变慢"

按这个顺序查:

```sql
-- 1. 有多少运行卡在 running?
SELECT status, count(*) FROM runs GROUP BY status;
-- 2. 数据库连接是不是满了?
SELECT count(*) FROM pg_stat_activity WHERE datname='ruixue';
-- 3. 有没有长事务卡住连接?
SELECT pid, state, query_start, left(query,60) FROM pg_stat_activity
WHERE datname='ruixue' AND state <> 'idle' ORDER BY query_start;
```

池太小的典型症状就是"莫名其妙变慢"(请求在排队等连接),日志里看不出错。
